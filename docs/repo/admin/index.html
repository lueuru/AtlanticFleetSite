审核后台（站长） ​

仓库有一套网站后台：玩家上传的 Mod 全部进「待审核」，你在后台点「通过」才会上架，点「驳回」则退回。这一页讲怎么用它。

本页含运维操作，请勿公开张贴

里面出现的地址、命令请勿转发到公开群聊，避免被人拿去尝试未授权操作。

后台在哪 ​

打开仓库页，右上角点「管理后台」，或直接访问 /admin/。

进入前要输一次管理员密钥。输对了会记住，下次打开直接进；换浏览器 / 清了缓存要重输。

后台怎么看数据 ​

顶部四个指标：

指标含义
待审核等你处理的提交，最该关心的数字
仓库在架仓库里当前真实可下载的 Mod 数
仓库总量仓库列表里的总条数（含历史手工放入的）
已驳回累计被退回的提交数

下面一排分类页：待审核 / 已上架 / 已驳回 / 全部 / 操作日志。

审一个 Mod ​

  1. 在「待审核」页找到那条记录；

  2. 点「详情」看完整 mod.json、上传者、来源 IP；

  3. 决定：

    • 通过并上架 —— 立刻写进仓库，自动生成分享码，所有人可下载；
    • 驳回 —— 退回，可附一句原因（作者能看到）。

已上架的记录还能「下架」（从仓库撤掉但不删记录）和「删除」（彻底移除，不可恢复，两段确认防误点）。

「已移除」标签是什么意思 ​

如果某条已上架的记录，在仓库包里找不到对应的文件（比如你手工把包删了），后台会给它打上「已移除」标签，并提供「重新上架」按钮。这样管理员一眼就能看出「数据库里说有，仓库里其实没有」的不一致状态。

操作日志 ​

「操作日志」页记录每一次通过 / 驳回 / 下架 / 删除，包含时间与操作对象。要回溯「这个 Mod 什么时候被谁下架的」，看这里。

重建索引 ​

「重建索引」按钮会以 packages/ 目录为准重新汇总仓库列表：

  • 手工拷进去的 Mod 会被正确收进来（不会被索引吃掉）；
  • 已删除的包会从列表里消失；
  • 数据库里没有元信息的老包，会从 mod.json 现推作者 / 版本 / 参数。

平时不需要手动点——上传通过 / 下架 / 删除时会自动重建。只有你手工动过 packages/ 目录时才需要。

自建一套同样的系统 ​

这套后台由两部分组成：

部分作用
网站前端mods/（仓库页 + 上传区）、admin/（审核后台）——纯静态，放 nginx 目录即可
后端服务一个零依赖的 Python 脚本（只用标准库），负责收上传、存数据、生成分享码

后端跑起来只需要 Python，不需要装任何第三方库、不需要数据库（数据用 SQLite 单文件存）。

目录约定 ​

mods/                      ← 网站根下的仓库目录
  index.html               ← 仓库页（含上传区）
  index.json               ← 仓库清单（网页与游戏端共用这一份数据）
  af-naval.css / .js       ← 共享设计系统
  packages/                ← 每个 Mod 的 .json 包 + .txt 分享码
  uploads/                 ← 上传的原包体（存底）
admin/
  index.html               ← 审核后台

后端会自动：

  1. 校验上传的 mod.json（格式、必填、重名、内容重复、大小）；
  2. 用内容哈希给每个 Mod 生成不冲突的 ASCII 别名（中文名才不会互相覆盖）；
  3. 过审时写包 + 生成 AFMOD1: 分享码 + 重建 index.json；
  4. 记录来源 IP 与完整操作留痕。

关键设计（踩过的坑） ​

两个真踩过的坑，自建时务必注意

1. 重名覆盖：早期用中文名生成 ASCII 别名时会退化成同一个 mod，导致后发布的把先发布的覆盖掉，三个人下载到的是同一个包。现在改为：无 ASCII 可用时用 md5(名字)[:8] 生成 mod-<8位> 保证唯一。

2. 「已上架」数字虚高：如果后台只数数据库里的 approved 记录，一旦有人手工删了 packages/ 里的包，后台还会说「已上架 N」，和仓库对不上。现在以 packages/ 目录为权威来源统计，两边永远一致。

备份建议 ​

真正要备份的是两样：

要备份说明
上传的源包packages/ 里的 .json（含每个 Mod 的完整内容）
数据库审核记录、留痕、来源 IP

index.json 随时能从 packages/ 重建，不用单独备份。
