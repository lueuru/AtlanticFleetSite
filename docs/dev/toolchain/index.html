逆向工具链（Linux 可复现） ​

想看懂这个游戏内部长什么样、或者给它做第二语言版本？这一页给出在 Linux 上从零搭起来的完整工具清单， 以及我们用它量出来的几个结论。每条工具都附验证证据，不是"装上了就算"。

一句话原则

工具装好不算数，跑通真样本 + 故意喂坏数据会报错，才算数。

为什么讲这个 ​

《大西洋舰队》是 Unity 4.7 / Mono / .NET 3.5 的安卓包。它的结构决定了工具选型：

层内容需要的工具
classes.dexJava 层（Unity Player + 渠道 SDK）jadx / apktool
assets/bin/Data/*.assetsUnity 序列化资源（场景、材质、字体）UnityPy
Managed/Assembly-CSharp.dll游戏逻辑本体 + 全部 UI 文本ilspycmd

先记住这条实证结论

我们用工具量过：三个资源文件里文本型 TextAsset 数量为 0，只有 4 个字体资源。 游戏的 UI 文本 100% 在 Assembly-CSharp.dll 的字符串里，不在资源层。 所以做本地化的主战场是 DLL，不是 assets。别在错误的地方挖。

工具清单（版本 + 实测耗时） ​

用途工具版本实测
.NET 反编译ilspycmd9.1.0.7988反编译 509KB 游戏 DLL → 24.7s
dex → Javajadx1.5.1104KB dex → 35 个 .java，8.9s
APK 解包/回包apktool2.7.091.8MB 包全量反汇编 → 10.8s

装法要点 ​

bash
# ilspycmd：不要用 `dotnet tool install`（那需要 700MB 的 SDK）
# 直接取 NuGet 包解压，配 .NET 8 运行时即可
curl -o ic.nupkg https://api.nuget.org/v3-flatcontainer/ilspycmd/9.1.0.7988/ilspycmd.9.1.0.7988.nupkg
unzip ic.nupkg -d ilspycmd
dotnet ilspycmd/tools/net8.0/any/ilspycmd.dll --help

版本要挑，不是越新越好

ilspycmd 11.1 的 NuGet 包目标框架是 net10.0，要 .NET 10；我们只有 .NET 8 运行时。 挑版本时逐个解包看 tools/<TFM>/ 目录，选与目标运行时精确匹配的那个（我们是 net8.0）。

一定要关掉联网更新检查

ilspycmd 每次启动都会去 NuGet 查最新版本，网络受限时会长时间卡住。 实测：--help 从 17.5s 降到 0.54s，整 DLL 反编译从 13m24s 降到 24.7s。

bash
ilspycmd --disable-updatecheck ...   # 自动化场景下必须加
1

两个自研小工具 ​

dex 字符串表解析 ​

改 dex 用的是「字符串槽位法」（原地等长改写）。下面两条红线踩了就出包崩溃：

  1. 字符串头里的 utf16_size 是字符数，不是字节数
  2. string_ids 必须按内容字典序排列
bash
# 列字符串（含中文的）
venv/bin/python bin/dex_strings.py classes.dex --cjk
# 打包前自检字典序
venv/bin/python bin/dex_strings.py classes.dex --sort-check

打包铁律复核 ​

bash
venv/bin/python bin/apk_ironrules.py 产物.apk --dll patched.dll --base 基底.apk
1

六组判据：STORED 集合与基底一致 / dex adler32+SHA-1 / 字符串表字典序 / 汉化署名 / DLL 内容一致 / 签名块存在。每组都带反证。

判据自己错过三次，别重蹈覆辙

  1. 13 个 STORED 清单硬编码猜名字 → 全错，一上来就误报。改成 「STORED 集合必须与只读基底 APK 逐项一致」——基底是真机可装包，跟它对不上就是打包链路坏了。
  2. dex magic 只比 4 字节 → 好 dex 被判"非标准"。magic 是 8 字节 dex\n035\0。
  3. 署名 tag 猜成 AFMOD1:，实际是 dex idx 555 的 You are playing 汉化版 by uruban。

用这套工具量出来的结论 ​

一、渠道 SDK 剥离是真实生效的 ​

原包里 classes2.dex 有 14 个 com.byfen.authentication 的类（防沉迷 / 实名认证）。 我们逐个验证：

检查点结果
Manifest 里 com.byfen 组件0 个（只剩 Unity 的 3 个）
主 dex 里 byfen / authentication 引用0 处
classes2.dex 里的 SDK 类14 个，但无人引用

那 14 个类是永不加载的死代码——这是对的：删掉它们会让 dex 偏移整体重排， 与「原地等长改写」直接冲突。留着但不引用，才是正确终态。

二、本地化覆盖率要用对判据，否则数字会骗人 ​

我们第一版审计跑出 31.3% 覆盖率，仔细一看，分母里混进了： 舰船代号 BB CA CV、倍率 1x 128x、单字母 A C E——这些根本不是 UI 文本。

修完判据后的真实数字：

494 条 UI 文本 → 中文 121 / 纯英文 373
其中 373 条纯英文里，350 条是不该翻的（路径 / 内部键 / 代号 / 倍率）
真正玩家可见的漏网：23 条
1
2
3

两条踩过的坑，记下来防复发

  1. 别用字节扫描找中文：把任意二进制按 UTF-16LE 解码，必然撞出假中文。 我们一开始扫出"原版 DLL 含 54332 个汉字"，结果是全假阳性，直接作废。 要看文本就去反编译产物里看。

  2. 提取字符串字面量的正则要排除换行：[^"\\] 会匹配换行， 于是把 C# 源码当成字符串捞了进来。必须写成 [^"\\\n]。

  3. 汉字总数差 ≠ 漏翻字数。我们拿 Windows 成品和 Linux 重建比， 汉字 7739 vs 7519，看着像丢了 220。逐条比对后发现差异里混着两类 不是丢失的东西：措辞差异（「准备飞机」vs「飞机就绪」）和 结构性差异（Windows 那版多几个功能，凭空多上百条字符串）。 真实缺口只有 20 条。要量准就用集合差集，别用总数。

三、判据对齐后，汉化追平了 Windows 成品 ​

最终口径：取两份反编译产物里「仍是英文的 UI 文本」集合做差， Linux残留 − Windows残留 就是漏翻的，目标打到 0。

汉字数     Windows 7739  →  重建 7765（反超）
覆盖率     Windows 70.4% →  重建 70.5%
残留英文差集（重建 − Windows） = 空集
补丁条数   166 → 188 → 208      DLL 508,928 B 全程未变
1
2
3
4

判据换过四次才对：汉字总数差 / difflib 字面量对齐 / 行级对齐都失效 （两份代码行号漂移、有 100+ 字面量的结构性增减），最后靠集合差集才量准。

Reverse-Engineering Toolchain (English) ​

Want to see how this game works inside, or build a second-language version of it? This page lists the full toolchain we set up from scratch on Linux, plus what we measured with it. Every tool comes with verification evidence — "it installed" is not the same as "it works".

Which layer holds what ​

LayerContentsTool
classes.dexJava layer (Unity Player + channel SDK)jadx / apktool
assets/bin/Data/*.assetsUnity serialized assets (scenes, materials, fonts)UnityPy
Managed/Assembly-CSharp.dllGame logic + ALL UI textilspycmd

Measured, not assumed

Across the three asset files there are zero text TextAssets — only 4 font assets. 100% of the UI text lives in the strings of Assembly-CSharp.dll, not in the assets. So localization happens in the DLL. Don't dig in the wrong place.

Tools (versions + measured timings) ​

PurposeToolVersionMeasured
.NET decompileilspycmd9.1.0.7988509KB game DLL → 24.7s
dex → Javajadx1.5.1104KB dex → 35 files, 8.9s
APK unpack/repackapktool2.7.091.8MB APK full decode → 10.8s
Unity assetsUnityPy1.25.4108MB asset → 2618 objects, 3.6s
IL disassemblyikdasm (mono)6.8equivalence checking
C# recompilemcs (mono)6.8replaces Windows .NET 3.5 csc
Sign / alignuber-apk-signerv1.3.0v1/v2/v3 in one pass

Newest is not always right

ilspycmd 11.1 targets net10.0 and needs the .NET 10 runtime; we only have .NET 8. Unpack candidate versions and check the tools/<TFM>/ folder — pick the one matching your runtime (net8.0 for us).

Always disable the update check

ilspycmd queries NuGet for the latest version on every start, which blocks badly on a slow link. Measured: --help went from 17.5s to 0.54s; a full DLL decompile from 13m24s to 24.7s.

bash
ilspycmd --disable-updatecheck ...
1

Two home-made helpers ​

Keep one implementation per fact

We once wrote a second inline DEX parser inside another script; for the same classes2.dex one reported 1 ordering violation and the other 0. Two implementations of one fact means you don't know which to trust. We deleted the inline copy and standardized on bin/dex_strings.py.

DEX string table parser ​

Editing a dex in place ("string-slot method") has two red lines:

  1. utf16_size is a character count, not a byte count
  2. string_ids must stay in lexicographic order
bash
venv/bin/python bin/dex_strings.py classes.dex --cjk
venv/bin/python bin/dex_strings.py classes.dex --sort-check

45 characters, 55 bytes — the 10-byte gap is exactly 5 CJK characters × 1 extra byte each.

What we measured ​

The channel SDK strip is genuinely effective ​

classes2.dex originally held 14 com.byfen.authentication classes (anti-addiction / real-name verification):

CheckResult
com.byfen components in the manifest0 (only Unity's 3 remain)
byfen / authentication refs in the main dex0
SDK classes in classes2.dex14, but unreferenced

Those 14 classes are dead code that is never loaded — and that is correct. Deleting them would reflow every dex offset and break the in-place edit strategy. Keep them, keep them unreferenced.

Localization coverage needs honest criteria ​

Our first audit reported 31.3%. The denominator was polluted with hull codes (BB CA CV), zoom levels (1x 128x) and single letters (A C E) — none of which is UI text.

After fixing the criteria:

494 UI strings → 121 Chinese / 373 English
of those 373 English, 350 must NOT be translated (paths / internal keys / codes / zoom levels)
genuinely visible to players: 23
1
2
3

Two traps worth remembering

  1. Never hunt for CJK by scanning raw bytes. Decoding arbitrary binary as UTF-16LE always yields fake Chinese — our first scan reported "54,332 CJK characters in the original DLL". All false positives. Read the decompiler output instead.

  2. Exclude newlines in the string-literal regex. [^"\\] matches newlines, so C# source gets captured as if it were a string. Use [^"\\\n].

  3. A CJK character count gap ≠ missing translations. Comparing the Windows release against our Linux rebuild gave 7739 vs 7519 — seemingly 220 lost. Itemised comparison showed the gap mixes in two things that are not losses: wording differences (「准备飞机」 vs 「飞机就绪」) and structural differences (the Windows build has a few extra features, adding 100+ strings). The real gap was 20 entries. Measure with set differences, not totals.

Criteria alignment: parity with the Windows release ​

Final yardstick: take the set of UI strings that are still English in each decompiled build and diff them. Linux-remaining − Windows-remaining is the miss list; the target is zero.

CJK chars    Windows 7739  →  rebuild 7765 (ahead)
Coverage     Windows 70.4% →  rebuild 70.5%
English-only delta (rebuild − Windows) = empty set
Patch count  166 → 188 → 208       DLL stays 508,928 B throughout
1
2
3
4

It took four attempts to find a criterion that works: total-CJK gap, difflib literal alignment and line alignment all failed (line numbers drift; the two builds differ by 100+ literals structurally). Only the set difference measured it correctly.

Packaging iron rules ​

bash
venv/bin/python bin/apk_ironrules.py out.apk --dll patched.dll --base base.apk
1

Six checks: STORED set matches base / DEX adler32+SHA-1 / string table ordering / localization signature / DLL identical / signature block present. Each carries a negative test — feed it broken input and it must go red.

Our own criteria were wrong three times before they were right:

  1. A hardcoded list of 13 STORED entries, with guessed names → all wrong, false alarms immediately. Now it compares the STORED set against the read-only base APK; the base is known-installable, so any mismatch means the packaging step broke it.
  2. DEX magic compared with only 4 bytes → valid DEX files judged "non-standard". The magic is 8 bytes: dex\n035\0.
  3. Signature tag guessed as AFMOD1:; actually it is You are playing 汉化版 by uruban at DEX string index 555.
